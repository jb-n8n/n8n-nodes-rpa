# Changelog

All notable changes to `n8n-nodes-rpa`, the `rpa-browser` image and the Windows package. Versions follow
[Semantic Versioning](https://semver.org/); until 1.0, a minor version may change behavior. The node is released with
`v<version>` tags, the image with `browser-v<version>` tags, the Windows package with `desktop-v<version>` tags.

## Unreleased

- **A failed desktop step names its step.** When the desktop runner refuses a step, the error is `Step N (intent): ` followed by the runner's own sentence without its error code, for example `Step 2 (Click Copy): found 2 buttons named "Copy". …`; the runner now words the three most common failures itself.
- **A blocked request is named.** When a run or an import's replay stops on a request the policy blocks, the message now names it as a Site Login line does, method, host and path (never the query string or the fragment; a session segment such as SAP's `/sap(…)/` masked), and says where it can be let through: for a POST, `a blocked request was attempted during the run: POST sandbox:8080/sap(…)/bc/gui/sap/its/webgui. If it only reads data, list it in the RPA Site Login under Requests That Only Read, as POST sandbox:8080/sap*/bc/gui/sap/its/webgui; if it saves or sends, only a step that submits may send it, listed under Forms It May Submit.`; for another method, `… DELETE host/path. Only a step that submits may send it, listed in the RPA Site Login under Forms It May Submit.`; for a page whose address looks like an action (replays and repairs), `… GET host/path. Its address looks like an action (such as delete, send or sign out), which this run does not open.` Before, the message was only `a blocked request was attempted during the run`, which other blocked requests (web sockets, refused sign-ins) still give. The README's sandbox set-up now lists the sandbox's two Requests That Only Read in its Site Login.
- **The review page of template 5 for desktop steps.** A candidate write that presses a key in a field where a secret variable is typed (Enter in the password field, which signs in), or with no target right after such a field is filled, starts unticked; it stays in the list. For a recording, the steps the import added (a wait for each window, the returned file) are shown in grey with their numbers, under one grey line such as `12 recorded steps, plus 5 the import added (waits for each window, the returned file)`. Import Steps gives both on the desktop draft of its Data output, as step numbers, `signInKeys` and (for a recording) `addedSteps`; they are shown only, never signed or reviewed. After the review page, the last page downloads the workflow file only when a step list was approved: a rejected bot gets the page without a file.
- **The rpa command in the credentials.** The hidden-token refusal now says `On that machine, in an administrator PowerShell, run & "C:\Program Files\RPA Runner\rpa.cmd" connection -ShowTokens and paste the line it prints.`, and the RPA Desktop Runner and RPA Browser notices and the runner's fingerprint texts name `rpa connection`, as the installer's closing lines do, where they named `Show-RpaConnection.ps1`.
- **The approver typed once.** Sign Steps' **Approved By** may now be left empty when the **Approver Allowlist** holds exactly one address (the same address written twice, in any case, counts as one): that address is recorded as the approver, spelled as in the allowlist. With more than one address, an empty Approved By is refused as before, now with `Sign Steps refused: Approved By is empty, and the Approver Allowlist holds more than one address: set Approved By to the one who decided`. A given Approved By must still be on the allowlist, and the allowlist must still be typed (an expression there is refused). Approved By is no longer marked required in the editor. Template 5 has the address in one place: its **Settings** node no longer holds `approver`, **Sign steps** leaves Approved By empty, and step 4 of its Set once checklist says `Type your address once, in **Sign steps → Approver Allowlist**: it is recorded as the approver.` Template 3 (approval by email) is unchanged: its emails need the address in Settings.
- **The signing key without a terminal.** The RPA Step Signing credential no longer names `openssl rand -hex 32`: its notice says to use 32 or more random characters, for example a password your password manager generates, and the Signing Key's hint says `Let your password manager generate a password of 32 or more characters, and paste it here`. A key shorter than 32 characters is refused as before, now with `The Step Signing key must be at least 32 characters (let your password manager generate a password of 32 or more characters)`. n8n's credential screen cannot generate a value: n8n 2.45's credential types have no generated default and no button that fills a field.
- Import Steps: keyboard shortcuts become steps. A UiPath **Send Hotkey** or **Keyboard Shortcuts** in a browser, and Playwright `press(…)` and `keyboard.press(…)`, become a `press` step per chord (on the activity's or locator's element, else on the one that has the focus), in the step's spelling (`Control+a` is `Ctrl+A`, `ArrowDown` is `Down`); in a desktop app, Keyboard Shortcuts become `key` steps as Send Hotkey already did. A chord the step refuses (a key that types a character, a Windows-key or shell chord, a Meta chord) is reported as not translated with the step's own reason, never spelling out a key that is not a named one; text typed through Keyboard Shortcuts is not a shortcut and is reported. A press on a password field is reported as not translated (`press` refuses one when it runs). Enter alone does what it did: a sign-in's submit, otherwise reported as before. A Tab pressed between a sign-in's fields is dropped as part of the sign-in step, which moves between its fields itself.
- Import Steps, UiPath: the UI activities inside a block are imported, in order, as if the block were not there, and the block is reported once, saying what that changes. Before, a block the import had no step for was reported and everything inside it was left out, so a project built from these blocks (the standard state-machine template among them) imported nearly empty. **Retry Scope**: its activities once (the steps do not retry; n8n's Retry On Fail runs all the steps again). **Try Catch**: the Try (and the Finally) as before, now with an item for the block; each Catch is listed as not imported with how many activities it holds. **Check App State**: the steps under "Target appears" get `when: { visible }` on its element and those under "Target does not appear" `when: { hidden }` (desktop steps only `visible`); each step checks the element again just before it runs, and the report says so. **Element Exists** followed by an If on its answer (`[found]`, `[Not found]`) does the same for the If's Then and Else. When the element cannot be read, or a branch holds more than UI activities, the block becomes an n8n If whose condition the person fills in, as an If on a variable already does. **While** and **Do While**: the body once, listed as not imported (the repetition): give Run steps one item per repetition. **Parallel For Each** becomes an n8n loop, as For Each does. **Switch**: one n8n If per case, Default last. **Flowchart** with decisions: every path, True before False, with each decision listed as not imported (every run now takes all paths); the decision is no longer a flow node, so the UI steps around it stay one run. **State Machine**: each state's entry once, from the initial state along the transitions and final states (End Process) last, with an item per state that names the steps it gave; the transitions are listed as not imported, except a transition or exit that only logs or comments, which is reported as not needed. An activity with a body the import does not know is reported as before, with nothing inside it imported. The rules for secrets hold inside a block as at the top level: a typed secret is removed, a desktop step that may write is only a candidate, and a condition that names a sign-in value removes its step.
- RPA Desktop Runner and RPA Browser credentials: a **Connection Line** field. Paste the one line the Windows installer prints at its end for the runner (`rpa-runner://<address>:<port>/rpa/v1#token=<token>&fingerprint=<64 hex digits>`) or for the browser (`rpa-browser://<address>:<port>/#token=…&fingerprint=…`); `Show-RpaConnection.ps1 -ShowTokens` prints them again. When the line is filled, the node takes the address, the token and the certificate fingerprint from it and does not use the separate fields (Runner URL, Token and Certificate Fingerprint; Endpoint URL, Token and Certificate Fingerprint in Browser Server mode); when it is empty, everything works as before, and the separate fields are no longer required on their own. The line holds the token: it is a password-type field that takes no expression, and no message repeats it. A line of the wrong kind, a missing part, a port outside 1 to 65535, a fingerprint that is not 64 hex digits (pairs joined by colons are accepted, as in the fingerprint field) or the installer's hidden token (`token=<hidden…>`, printed without `-ShowTokens`) is a configuration error that says what is wrong and what to do. The certificate fingerprint check itself is unchanged. The credentials' Test button works with the line alone.
- A new credential, **RPA Secret Variables** (`rpaSecretVariablesApi`): name and value pairs, each value a password-type field, attached to Run Steps. Run Steps adds them to the run variables as secret variables, for browser and desktop runs alike. A secret variable's value is masked from the start of the run, whether or not a step uses it: in the Data and error items, the step log, messages, traces, the text of failure and step screenshots, and what the chat model sees (page text and the variables in its prompt). Only signed steps type one: in the browser a fill with `secret: true` (as before), on the desktop a fill whose value is exactly `{{var.name}}`; unsigned desktop steps that would type one fail `policy_violation` (`Unsigned steps cannot type a secret variable. …`). Any other use of the value, such as a plain fill, a locator, a select option, a URL, text around the template or a `when` condition on it, is refused with `an input value contains a credential secret`. A value shorter than 4 characters is refused (a value that short cannot be masked without also hiding ordinary text: put it in Options → Variables if it is not secret), as is a name given both there and in Options → Variables; these messages name the variable, never its value. A value that is also a Site Login secret is masked but never typed by a secret fill. The credential's Test button checks the names and values and lists the names. A run that stops on a variable nobody supplied still fails with `missing input "<name>"`, now followed by `(a secret goes in an RPA Secret Variables credential, any other value in Options → Variables)`.
- With a secret variable or a value a browser secret fill types (also from Options → Variables), a screenshot step now masks the form fields and the text of those values, and a screenshot or PDF of a page that shows one is refused (`the page shows a credential`), as it already was with a Site Login.
- Options → **One-Time Code Workflow** (Run Steps and Import Steps) is now n8n's workflow picker: pick the workflow from the list, or give its ID. A workflow saved with a typed ID keeps working. It must be set directly: an expression is now refused (`One-Time Code Workflow must be set directly, not with an expression.`), so item data never chooses which workflow the node runs.
- **Every import ends in a workflow that runs.** Import Steps now writes binary `workflow` for every source with steps: a Chrome recording, Playwright code and a step document get one **Get active steps** → **Run steps** pair per step list, named by it, as a UiPath project and an RPA recording already did. Every generated workflow starts with **Run the bot** (a manual trigger) and **On a schedule**, a Schedule Trigger that is switched off with the note "Set the time, then turn this node on and publish the workflow". The Run steps nodes carry the options the import ran with: the One-Time Code Workflow (written as n8n's workflow picker, by ID) and its Code Timeout when not 120, Max Seconds when not 180, and Also Allow These Sites on browser steps. **Allow Private Network** is never set: a browser Run steps' note says to turn it on for a site on your own network. The run variables a browser step list types are listed under Options → Variables to fill in. A browser Run steps is generated without its repair branch (AI Repair off, no Chat model, no Approve steps), for UiPath projects too, so the workflow runs as generated with only the credentials Set once names; its note says in three lines how to add self-repair (a chat model, AI Repair with a Goal, an Execute Workflow that calls RPA: 3 Approve steps). Before, a UiPath project's browser sequences came with a Chat model and an Approve steps that had to be set up before the workflow would run or publish. The generated texts say that steps are approved on the review page of **RPA: 5 Import a bot**.
- **Start values for a recording's variables.** The recording format `rpa-recording/1` gains an optional `variables` object, a variable's name and the value that was recorded where the person made it a variable (one line of at most 500 characters). The RPA recorder writes it (`Rpa.Recorder.Core`: a variable made with Make it a variable keeps the value its step held, tied to that step: a step made secret, deleted or renamed takes its start value with it; two steps sharing a name start with the first one's value; no start value is written for a secret variable's name, nor one equal to a value made secret in the session, nor a value of several lines). Import Steps refuses a start value for a secret variable (in `secretVariables`, or typed by a fill marked secret), for a variable no step types, and one that holds a value of the RPA Site Login. The start values are not in the signed steps: the Data output's draft carries them as `startValues`, the generated workflow starts each variable with its value ("The Variables start with the values that were recorded"), and the review page marks such a step "variable in_CompanyCode, starts as 2000". A file without the key imports as before.
- **Secret variables come from the RPA Secret Variables credential.** A generated Run steps no longer lists a secret variable (a recording's password, a secret fill's variable) under Options → Variables: its note names the variables to put in an **RPA Secret Variables** credential (type `rpaSecretVariablesApi`, field Variables) and select on that node, and the Set once sticky lists them. No other way of supplying a secret is described.
- **One name.** A recording and every other source that gives one step list keep the Name the person typed (`line-item-export`, where a recording used to give `line-item-export-1`); a UiPath project keeps `-1`, `-2`. The review page, the table row and the generated workflow show that name. The recording import is not released, so no stored row changes.
- **Import Steps works out the source.** **Source** has a new first choice, **Work It Out From the File**: the file name decides (`.rpa-recording.json` a recording, `.zip` or `.xaml` UiPath, `.js` or `.ts` Playwright code), else a ZIP's first bytes, else the JSON's shape (an RPA recording, a Chrome Recorder export, a step document). A file it cannot place is a configuration error: `Import Steps could not tell what the file holds: give it the name its tool saves (.rpa-recording.json, .zip, .xaml, .js or .ts), or choose its Source.` The default for a new node stays Chrome Recorder. Template 5's form makes **Source** optional (to start with: Work it out from the file) and asks for the downloaded file's name pattern and columns on a second page, **The file it downloads**, only when the upload is not a recording or a UiPath project.
- **A refused sign-in that names a missing login page can be imported again.** When an import fails because an address is not listed under the RPA Site Login's **Pages Where the Password May Be Typed**, template 5 shows the page **Add the login page**: the refusal as the import words it, what to add where, and an **Import again** button that imports the same file once more, with the Site Login as it is then.

- **Template 5 approves on its own form.** By default the person who imports a bot now reviews and approves it on the next page of the **RPA: 5 Import a bot** form, and needs neither **RPA: 3 Approve steps** nor a mail server. This moves the default approver: before, a second, named person approved by email; now the person who imports approves, and approval by a second person by email is an option (next entry). Anyone who can open the form (its Basic Auth credential) can now approve and sign, and Approved By records the address on Sign steps' Approver Allowlist, not who opened the form. After **Import steps**, the page **Review and approve** shows every step list on Repaired Steps, one block each, short first: the name and version as its title, a few lines on what the steps do besides reading (the app or the sites, a sign-in, a form they submit, a file they return, what the replay proved), the steps the import left out (when there are any), and the steps as a numbered list, each worded from the step itself as the recorder's bar words it (`Type "clerk" into User name`, `Choose "2000" in Company code`, `Press Enter in Password`), marked where it uses a variable or a secret variable (by name; a secret variable never shows a value) or returns a file. The page ends at the decision: one grey line says that how each step finds its control is in the run's execution in n8n and in the approval email. A new Settings value, `showDetails` (false to start with), puts each item's own safety flags, evidence and change list, as Sign Steps compares them, back on the page above the question. The short view is built from the item's own steps, flags and left-out steps. For desktop steps it asks "Which of these steps save, send or submit?" with one tick box per candidate write, ticked to start with (the person approving here recorded or imported the bot and is looking at the list), one grey sentence (`Ticked steps are allowed to save or send. An unticked step is stopped only when it tries to use a control or key that your administrator has protected on the bot machine.`), and an optional field for the number of any other step; then **Decision**: Approve and sign, or Reject, for each step list. **Sign steps** gets each step list exactly as Import steps gave it, in the order of the page, with that block's decision and the numbers of the ticked and typed steps as Write Steps; Sign Steps recomputes and compares the shown texts as before. An approved list is written as an `active` row of `playwright_steps` and every other active row of its name becomes `superseded`; a rejected list is written as a `rejected` row with no steps and no signature; a list Sign Steps refuses (a step number that does not exist, an approver not on the allowlist, a missing credential) writes no row. A page left unanswered for an hour signs nothing and writes no row. The last page says, for each step list, `Approved and signed: <name> v1 is now the version that runs under that name.` (with the steps signed as writes), `Rejected: <name> v1. Nothing was signed.` or `Not signed: <name> v1. <reason>`, and still downloads the workflow file of a UiPath project or a recording. Screenshots of a browser replay are not on the page (an n8n form page shows only images from web addresses): the page says they are on the Repaired Steps output of Import steps in the execution. A new **Settings** node after the form holds `approval` (`on this form`, the default, or `by email`); the approver's address is typed in **Sign steps → Approver Allowlist**, which must stay typed so that item data cannot choose who may approve.
- **Approval by email is the option.** With `approval` set to `by email` in template 5's **Settings**, each step list goes to **RPA: 3 Approve steps** as before. Template 5's **Approve steps** node ships switched off, because n8n publishes a workflow only when an enabled Execute Workflow node names its workflow, and the default path needs none: the grey sticky **Approval by email** says to import and publish workflow 3, choose it in **Approve steps** and turn the node on. With `by email` and no workflow chosen, the last page says that nothing was sent for approval. In template 3, desktop steps now get one email, `Approve desktop steps v<version> for <name>?`, with the flags and the numbered steps and a **Review and decide** button, where before they got a review email and an approval email; the email lists the steps by their intents with the full detail below, and its form asks **Decision** (Approve and sign, or Reject) and has the candidate writes as tick boxes, none ticked to start with (a second person decides unprompted), and a field for the number of any other step. Browser steps keep two emails: n8n's send-and-wait email cannot carry attachments, and the review email carries the screenshots. Template 3's **Settings** now holds `approver` too: the four emails' To, Approved By and the rejection's approvedBy read it, so the address is typed twice (Settings and the Approver Allowlist) instead of six times. Settings now comes first and passes the item and its screenshots on.
- **Tables on demand.** Templates 5 and 3 create `playwright_steps` and `playwright_runs` when they are missing (Data Table → Create, If Not Exists, with the columns template 1 creates). **RPA: 1 Create tables** is optional now; its sticky says so. Run it, or import a bot first, before **RPA: 2 Data feed** runs for the first time.
- **Set once notes are checklists** of at most six numbered lines in templates 3 and 5. What they used to explain: in template 5, keep **Authentication** on, because an anonymous form could start logins with the attached Site Login (the login breaker would trip) and spend on a chat model when one is attached; a UiPath project, a step document with only desktop steps, an RPA recording and a step document that goes to approval not replayed need no RPA Browser credential, since nothing of them runs; the RPA Site Login on **Sign steps** must be the one **Import steps** used, because the signature binds it; a step document with `{{var.name}}` values needs each one under **Options → Variables** in **Import steps**; to add a chat model, turn on **AI Repair** in **Import steps** and connect a model to its **Model** input (it repairs an imported browser step that no longer finds its element; without one such a step fails the import with the step that drifted). Workflow 3 needs publishing before template 5 only for approval by email. In template 3, desktop signatures bind the app, never a Site Login.

- Windows package: the RPA recorder, `RpaRecorder.exe`, in the package's `recorder\` folder (the installer refuses a package without it). It watches a person work in a Windows app and saves a recording file for Import Steps (source **RPA Recording**) and a policy change file for `RpaPolicy.exe apply`; a field it recognises as a password box (by its password flag, or a name or id that reads like one) is not read, a value marked secret afterwards is removed from the list and the file, and Import Steps refuses a recording that still carries a value in such a field. Import Steps leaves out a recorded key that drives the Windows shell (such as Alt+Tab) and a choice of an empty item, each with a report line, and imports the rest. The Windows install guide has a new section 12, Recording a flow. Tried on WinForms and Win32 apps, not on WPF, WebView2 or apps that draw their own controls. Import Steps no longer shows Start URL, AI Repair, Goal and ID Pattern for the source RPA Recording, where they did nothing.
- The RPA recorder's bar is rebuilt to say what to do at every stage. Its top line gives the state in words with a coloured dot (`Ready`, `Starting <app>…`, `Recording <app> · <n> steps` in red, `Paused` in amber, `Finished`), and one sentence under it says what to do now. Ready offers **Start an app…** (one window: the program, with **Browse…** opening in Program Files, and **Arguments (optional)** with the note that arguments are saved in the recording) and **Use an app that is already open…**; Recording has **Pause** (**Resume**) and **Finish**; Finished has **Name** (it starts as `<program> recording`) and **Save**. The steps are numbered, long ones wrap, and the list scrolls to the newest step; a read says what the element showed (`Read "6 line items" as out_result_count`), while the file still names it by its id. Where the bar saves and lists what comes next it grows so that the list keeps six rows, and once saved the step actions show only when a step is selected. On a screen narrower than 1280 the bar starts 360 wide, and Ready says that it can be dragged. A value that is a variable, a secret, and a step to check (recorded late, found by its row position or by the text it shows, or a click on a label) carry a mark whose tooltip says why. **Delete step**, **Make variable…** and **Make secret…** are enabled only for a selected step they fit (a file name typed into a Save dialog stays as recorded, and a secret stays a secret); their questions open beside the bar, name the step and its value (`Make step 5 a variable`: `Step 5 chooses "2000" in Company code. …`) and show the name rule under the name box. The F9 question names the element by the text it shows (else its id) and suggests an output name from the id in words (`out_result_count`, was `out_lblresultcount`). Notices show one at a time on one line under the state line (a long one cut, whole in its tooltip), amber when something should be checked, with **Earlier notices** listing them all; the arguments warning moved into Start an app, and the Ctrl+Alt note shows only when such a key was pressed and not recorded. **Save** writes into `Documents\RPA recordings` (created when missing; **Change folder…** picks another) and still asks before it replaces a file; closing the bar and **Record another** ask first when the steps are not saved. After saving, the bar lists what comes next: **1. Allow <app> on this machine** with **Allow this app…**, which starts the install's `runner\RpaPolicy.exe apply` on the saved change file with a request for administrator rights (Windows asks; the tool shows what it allows and asks in its own window, as before) and then says whether the tool reported success; a recorder that is not part of an install under Program Files shows the command for an administrator instead. **2. Import the recording in n8n** with **Show the file**. The recorder itself changes no policy.
- Windows package: `RpaPolicy.exe apply` takes the change file from where it is, such as the recorder's `Documents\RPA recordings`. It reads the file once with the same checks as before, copies it as a new file into `policy-changes\` beside the policy file (a folder of the tool's own for administrators only: created when missing, and refused, as the backup folder is, when it is a link or someone else owns it, can change it or can create files in it), and shows and applies that copy. A change file that changes after the copy changes nothing. Each copy stays, named after the change file and the time, as a record of what the tool was given. Copying the change file by hand to a folder only administrators can change, as the Windows guide says today, is no longer needed.
- Windows package: `Get-Rpa.ps1 -Zip <path>` and `rpa policy apply <file>` take a relative path as it is typed. Before, a relative path was read against the folder of the process (`C:\Windows\system32` in an administrator PowerShell started from the Start menu) and `Get-Rpa.ps1 -Zip .\rpa-windows-x64.zip` failed with "Could not find file"; now it is read against PowerShell's current location, from which the full path is made and used. Nothing is read as a pattern and no link is followed; a place that is not the file system (such as `Env:`) is refused.
- Windows package: the installer adds one Start menu entry for all users, **RPA Recorder**, which starts `recorder\RpaRecorder.exe` in its folder (no desktop shortcut, no other entry). It is recorded in `install.json` before it is made, removed by a failed install and by `Uninstall-Rpa.ps1`, and made again by an upgrade. A shortcut of that name that the installer did not make is left as it is, with one line saying so.
- The RPA recorder asks once which values change from run to run. After **Finish**, when a step typed a value or chose an item, the bar shows one page in place of the list, **Which of these change from run to run?**: each such step with a tick box, its number and sentence as the list says them (`Type "clerk" into User name`), and under it the variable's name, filled in from the field's label (two fields that would get the same name get `date` and `date_2`). A ticked value becomes a variable as **Make variable…** makes it, starting with the value that was recorded. Nothing ticked is fine: **Continue** goes on to the name and **Save**. **Back** returns to the list with the recording paused (**Resume** records more; **Finish** shows the page again with the choices made). A secret shows as a secret, by its variable's name only, and stays one; a value made a variable while recording shows ticked, and its name can be changed there. A file name typed into a Save dialog is not offered (it stays as recorded). **Make variable…** and **Make secret…** stay on the bar for use while recording. Before, each value took four actions: select the step, Make variable…, a name, and confirm.
- The recorder's bar after Finish: the step actions no longer leave an empty band under them (they were measured at the width of the line above them and kept the height of three rows), so the list gets that space while recording, in Finished and in Saved. The bar grows until the list shows six rows as high as they are (a row that wraps counts as two lines), and when there is no room below it moves up, at most to the height of the working area, so that the list of a bar moved down does not vanish. **Delete step**, **Make variable…** and **Make secret…** stay on one row on a bar 360 wide. After saving, **2. Import the recording in n8n** also says that n8n lists a few more steps than the bar: a wait for each window, and one for each file the bot returns.
- Windows package: `RpaPolicy.exe apply` takes `--close-on-success`. In a window of its own, the tool then closes that window once the change is applied (or there is nothing to change) instead of asking to press Enter; after a refusal, a no, an error, or a runner that could not be restarted it still waits, so that the reason can be read. The recorder's **Allow this app…** starts the tool with it; run by hand, the tool waits as before.
- A run may last up to 600 seconds (Max Seconds, was 300), and a browser step's `timeoutMs` may be 100 to 300000 (was 120000). A longer run holds its browser session and its Site Login lock for as long as it runs. A Windows run's Max Seconds also rises to 600, while a Windows step keeps its 120000 limit.
- A browser step's `when` may now also be `{ hidden: <locator> }` (run only when the element does not show) or a run variable compared with literal text, `{ var, equals }` or `{ var, notEquals }`; write the opposite condition on the next step in place of an else. A variable condition is refused on `signIn`, `submit`, `download`, a `paginate` that holds a `submit` or `download`, the click that opens a write window, and a variable that a secret `fill` types. Step lists signed before keep their signature and run as before; a list that uses the new forms is refused by 0.2.0.
- Two new browser steps and a click with keys held: `press` sends one key chord (`{ key, target? }`: Enter, Tab, Escape, Backspace, Delete, arrows, PageUp, PageDown, Home, End, F1 to F12, alone or after Ctrl, Alt and Shift, or Ctrl+A), `hover` moves the mouse over an element, and `modifiers` beside a `click` (`["Ctrl"]`, `["Shift"]`, `["Alt"]`) holds keys during it. A key that types a character, a paste and `{{var.name}}` in `key` are refused, and so is a `press` on a password field. `press` is not a declared write: an Enter that would post a form is refused like a click on its button, and an Enter that sends a search by GET passes. Step lists signed before keep their signature and run as before; a list that uses the new steps is refused by 0.2.0.

the install guide, with a sample flow; [`docs/install/licensing.md`](https://github.com/jb-n8n/n8n-nodes-rpa/blob/main/docs/install/licensing.md) is a note on what
Microsoft's terms say about unattended automation on Windows (not legal advice).

### Desktop steps

- **Desktop step sets** (`"surface": "desktop"`): Run Steps drives a Windows app through the RPA desktop runner, with
  the **RPA Desktop Runner** credential (runner URL, token, certificate fingerprint). UI Automation locators; the verbs
  `click`, `fill`, `select`, `check`, `waitFor`, `read`, `key` and `expectFile` (a file the app saved, returned like a
  download). Steps are signed and approved like browser steps; Sign Steps' **Write Steps** marks the steps that save,
  post or submit. 0.1.0 refuses desktop steps.
- **Import Steps** turns the desktop activities of a UiPath project into desktop step sets for approval, and the
  generated workflow runs each one on the RPA Desktop Runner credential.
- **The desktop runner** (`RpaRunner.exe`): a WebSocket server with TLS and a token, in the signed-in session of the
  bot user. A local policy on the Windows machine, which only administrators can change, lists the apps it may start
  and the controls and keys that count as writes. **The policy tool** (`RpaPolicy.exe`) shows a change to that policy
  in plain lines and applies it after an administrator says yes.

### Sign-in codes, locator variables, secret fill and clipboard reads (#54)

- **One-time code from a workflow**: a sign-in's `totp` can say `"source": "workflow"`; Run Steps runs the workflow
  named in **Options → One-Time Code Workflow** and types the code it returns (for a code from an email or an
  authenticator app). `totp.via` clicks through a factor choice or "Send me the code" page before the code field, and
  `totp.check` ticks boxes such as "Trust this browser" before the code is submitted.
- **Variables in locators**: `{{var.name}}` in the name of a role locator, in a visible text locator and in a desktop
  condition's `name`, rendered each run; refused in every locator of a step that writes or signs in. A `select` may
  take a list of values.
- **`fill.secret`**: signed steps can type a per-run secret from a variable into a password field; the value is
  masked from the start of the run.
- **Clipboard reads** for desktop steps (`read { clipboard: true, as }`), for apps whose value is only available
  through a Copy button. The runner returns only the run's own fresh copy, and only when its policy sets
  `clipboardRead`. Its policy can also list helper processes (`helperProcesses`), so that a web view app's elements
  resolve.

### A browser server with its own certificate

- **Certificate Fingerprint (SHA-256)** on the RPA Browser credential: in Browser Server mode with a `wss://` address,
  the node connects only to a server whose certificate has that SHA-256 fingerprint, and checks it before it sends the
  token. For a browser server with a self-signed certificate, such as the one the Windows package installs.
- **The gate** (`images/browser/gate`) can serve TLS, read its token from a file and listen on a chosen address. These
  settings need the `rpa-browser` image 0.2.0 or later: the 0.1.0 image does not read them.

### The Windows package

- `Install-Rpa.ps1` installs the runner, the policy tool, a browser host (Node.js, the gate with TLS, the browser
  server and Chromium) and the ERP Demo on Windows 10 1809 or later, Windows 11 or Windows Server 2019 or later. Both
  programs run in the bot user's session, started by scheduled tasks at that user's sign-in. The installer creates a
  standard local bot user or uses one you name, writes both tokens, limits the firewall rules to the addresses you
  give, and checks who can change the package and the data directory before it uses them. `-AutoSignIn` sets up
  automatic sign-in only when asked for, and lists what it changes first.
- `Show-RpaConnection.ps1` prints what the n8n credentials need: the URLs and fingerprints, and the tokens with
  `-ShowTokens`. `Uninstall-Rpa.ps1` removes the install and puts back what `-AutoSignIn` changed; `-RemoveData` removes
  the data directory too.
- The browser host opens the browser with a window on the bot user's desktop for every client that does not ask
  otherwise, so runs from n8n get a browser with a window. Save as PDF needs a headless browser and fails on it.
- The package is built, installed and driven end to end on Windows in CI (GitHub's `windows-latest`, Windows Server
  2025), and released from the `Desktop release` workflow after a reviewer approves it. It is not code-signed.
- **The desktop test bed**: `deploy/terraform/modules/aws-ec2-desktop-runner` (with an example and
  `deploy/scripts/desktop-testbed.sh`) runs the package on a Windows Server 2022 VM on EC2.

### Fixes

- **A rejected password is `login_failed`** without a `detect` step: when the site sends the password page back
  after `signIn` submitted it, the step fails with `login_failed` (`account_locked` when the page says the account is
  locked) and the login breaker opens. In 0.1.0 a hand-written sign-in passed, and the run failed later as drift (with
  AI Repair on, the model then tried to repair it).
- **The Allow Unsigned Writes option and the README now state what the switch hands over**: unsigned steps may sign in,
  so whoever can set the steps drives the Site Login.
- **A `paginate` whose body holds a `submit` or a `download` takes no `{{var.name}}` in its own `when`, `expect` or
  `next`**: they decide whether and how often the write runs. Run Steps and the schema refuse it when the steps are read.
- **Import Steps drops a recorded password from fields named in other languages**, not only English: Kennwort,
  contraseña, mot de passe, senha, wachtwoord, пароль, パスワード, 密码, 비밀번호 and more; such a field, and one named
  `pass`, starts the `signIn` as an English one does. In 0.1.0 a Chrome recording or Playwright code kept the typed
  password as a literal in the draft. Passenger, passport, compass and bypass fields are no longer stripped as
  password fields.
- **The approval emails say that the evidence and the change list are as reported by the run**: in **RPA: 3 Approve
  steps**, the review email's Evidence and What changed and the approval email's Evidence. Sign Steps recomputes the
  safety flags from the steps, not these. The desktop approval email (**Ask for approval (desktop steps)**) keeps its
  `Evidence:` label: its evidence is a fixed text and its change list is checked step by step. Import template 3 again
  for the new texts.

## 0.1.0 (2026-10-26)

First public release: the node `n8n-nodes-rpa` 0.1.0 on npm (the same tarball is attached to the GitHub Release, with
a build attestation) and the image `ghcr.io/jb-n8n/rpa-browser:0.1.0` (Playwright 1.63.0).

### The node

- **Quick operations**: Screenshot, Get Page, Save as PDF, Extract Data (table or list), Fill and Submit Form, Download
  File. A URL and one or two fields; GET only, except the form's own submit.
- **Run Steps**: a JSON list of browser steps for sites behind a login, with a Site Login credential (username, password,
  TOTP) whose secrets reach the page only through a sign-in step and are masked everywhere. Optional AI Repair: when
  the steps stop matching the site, a chat model finds the data in the same browser, the engine compiles its actions
  into new steps and proves them in a fresh browser with no model and no writes. The repaired steps carry the proof
  run's trace for the reviewer.
- **Sign Steps**: signs approved steps with an HMAC key; Run Steps refuses unsigned or edited steps by default.
- **Import Steps**: turns a Chrome Recorder export, Playwright code or a UiPath project into steps for approval. Typed
  passwords are never imported, imports never write, and what passes a fresh-browser replay comes out on Repaired
  Steps for Sign Steps. A UiPath import also returns the rest of the bot as an n8n workflow file, in which each browser
  sequence has AI Repair on and sends its repairs to approval.
  - An imported sign-in keeps a "Stay signed in?" answer (No, Yes or "Don't show this again") in the login block, and a
    code typed from a UiPath TOTP activity becomes the sign-in's code (the Site Login's authenticator types a fresh one).
  - With an Expected File, a dialog's confirming click (Continue, OK, Save) that ends the recording after the export
    click, with no address change or URL check between them, becomes the download.
- **Two-page sign-ins**: `signIn.next` for identity-first sign-ins (email, Next, password, as Microsoft Entra and Okta
  do); the agent and the importers build it. A rejected username is `login_failed` when the site sends the username
  page back; an inline error on the same page times out as drift, and AI repair is not attempted once the username was
  typed.
- **Self-healing downloads**: download steps can declare file checks (name, type, columns, rows), enforced on every run;
  AI repair of steps that download one checked file; **Expected File** for a first run; the file's facts as evidence in
  the review and checked by Sign Steps.
  - File checks find the header in the first 10 non-empty rows, and the CSV delimiter is the one with consistent
    per-line counts (semicolon files with decimal commas work).
  - A repair keeps the click of a failed download trigger that opened a dialog (for example an Export → format popup),
    shown in the change list as "Open <trigger>". When the agent itself tries a download on such a control and the
    click opens a dialog without a file, the click is kept as a successful click before the agent's dialog steps.
  - Downloads refuse a Chrome DevTools Protocol (CDP) browser connection up front with a configuration error: CDP
    cannot read downloaded files.
- **Requests That Only Read** on the Site Login: POSTs that only read (for example an OData `$batch` or a report
  screen's postback) pass in every run, are never counted as writes, and are listed in the review evidence.
- **Repairs**: typed filter values that equal one run variable compile to `{{var.*}}`, and the agent's prompt carries the
  run's variable names and masked values. Repairs no longer propose `#id` fallbacks on generated ids (SAP, UI5, React,
  Ember, hex salts) or `href` fallbacks carrying a session segment. A repair fills each field once. The agent sees what
  a field already holds, but never a value on a login page or in a credential-class field. Proofs open the work's entry
  page with the reused session, so sites that keep window state on the server (such as SAP GUI for HTML) prove.
- **Approval**: the approval text renders every value on one line and quotes values that could fake a clause. A pending
  Repaired steps item with an unsafe value, or a download step with no checks (shown as `checks: no checks`), is refused at Sign
  Steps once and must be produced again. When "RPA: 3 Approve steps" activates a version, older `active` rows of the
  same name become `superseded`.
- **Queue mode**: with several n8n workers, an **RPA Redis** credential on Run Steps shares the login breaker and the
  run lock between them; a lock left by a worker that died frees itself. In queue mode, Run Steps with a Site Login
  and no Redis credential is a configuration error.
- **Browser service**: runs wait up to 60 s for a free browser session, then fail `browser_unavailable` with "no free
  browser session"; the credential test passes when every session is busy. With Slow Motion on, a live view shows the
  running step in Browser Server mode too.
- **Step schema**: a JSON Schema of the step document (`dist/schema/steps.schema.json`) for editor autocomplete.
- **Templates**: Hello world, "RPA: 0 Connection check" (proves the browser reaches your site), the self-healing data
  feed (create tables, the feed, approve repaired steps) and "RPA: 5 Import a bot" (a form in front of Import Steps,
  with approval through "RPA: 3 Approve steps").
- **Safety**: a per-run site allowlist, checked on every redirect hop before the browser sends it, private networks
  blocked by default, writes only where steps declare them, a login breaker and a run lock per Site Login, scrubbed
  browser traces.
- **Browser connections**: a browser server over the Playwright protocol (such as Browserless or the `rpa-browser`
  image), Chrome DevTools Protocol, or a local browser for development. Slow Motion for live views and debugging.

### The browser service

- **The `rpa-browser` image**: Playwright's run-server behind a token gate, with a supervisor under tini. A session
  limit per replica (`503` busy), `/healthz`, Prometheus metrics on port 9464, drain on stop, and optional ECS task
  protection and CloudWatch EMF metrics. Published to GHCR for linux/amd64 and linux/arm64 with a build attestation.
- **Helm chart** `deploy/helm/rpa-browser` (KEDA, CPU or fixed scaling; NetworkPolicy; optional Cilium FQDN policy) and
  **Terraform modules** `k8s-browser` and `aws-ecs-browser`, with eks-attach, ecs-attach and EKS-managed
  (`terraform-aws-n8n`) examples. The token never enters Terraform state.
- `deploy/scripts/configure-n8n.mjs` creates the RPA Browser credential and imports the templates through n8n's public
  API; runbooks for Kubernetes and Amazon ECS in `docs/deploy/`.
